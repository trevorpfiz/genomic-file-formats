# Architecture: the developer contract

Read this before changing code. It summarises what M1 built (the shell, the design system, every exercise type, the Section 2 validators and Section 2 with its quiz) and the interfaces every module depends on. The plan (`docs/PLAN.md`) stays the source of truth for scope and behaviour; this file says where things live and how they connect. Commands and authoring rules are in `CLAUDE.md` and `docs/CONTRIBUTING.md`.

## 2. Content, ids and the manifest

- **Page kinds** (frontmatter `kind`): `lesson`, `quiz`, `capstone`, `page`. Schemas are `FRONTMATTER_SCHEMAS` in the compiler; unknown or missing keys fail the build. Lessons need `id, section, title, minutes (8-12), objectives (LO1-LO8), introduces, requires, caseBeat, specs` and may have `summary`. A quiz page's `id` is `quiz-<section>`. The `section` must be listed in `content/course.ts`.
- **Routes** (`CompiledPage.route`, D-22): `#/lesson/<id>`, `#/quiz/<section>`, `#/capstone`, `#/` (page `home`), `#/<id>` (other pages, for example `#/about`).
- **Ids.** Exercise and snippet ids are `<lesson-id>/<slug>` and must start with the id of the lesson that uses them. Quiz ids are bare section ids. DOM ids replace `/` with `--` (`exerciseDomId` in `src/shell/ids.ts`); heading ids are `slugify(text)` and never contain `--`. Routes to exercises use the DOM id: `#/lesson/fasta-reference/fasta-reference--why-wont-this-index`.
- **Manifest.** `content/course.ts` lists every page with `status` `built` (its file exists and compiles) or `planned`. Tests require every compiled file to be listed as built, and every built entry to have a file. Lesson `minutes` must equal the course map.
- **Concepts.** Ids look like `area.name` (`CONCEPT_ID`). `conceptIntroducers` maps each to the page that introduces it in main text. A built lesson's `introduces` must map to itself, its `requires` must be introduced by an earlier page, and every exercise's `concepts` must be introduced at or before its lesson. Section 2's vocabulary (`fasta.*`, `fai.*`, `compression.*`, `sequencing.*`, `quality.*`, `fastq.*`, `recognition.first-bytes`) and the Foundations concepts it requires are listed there; keep the frontmatter, the map, the exercises and the quiz slots in step.

## 3. Types (the data contract)

`src/exercises/types.ts` documents every field. In brief:

- **Vocabularies:** `FormatId`, `RuleId`, `Severity` (`error | warning | convention`), `Verdict` (`valid | invalid | unusable-here`), `Kind` (the seven types), `ObjectiveId`, `Tag` (`recognition | validity | application | concept | LO1…LO8`), `ConceptId`, `GoalCheckId`, `HelperId`, `VerificationId`.
- **Snippets:** `Snippet` (`text | hex | compressed-text`, `provenance`, `hideIdentity`, `download`, `view`, `columns`, `caption`), `HexView` with `HexAnnotation`s, and `RegisteredSnippet` (a snippet with an `id`, for `::snippet`). A caption shows where the snippet stands as a figure (`::snippet`, a predict's snippet) and renders inline marks.
- **`Validation`:** `{ format, profile, context?, severities? }` (default severities `["error"]`).
- **`ExerciseBase`:** `id, kind, title, prompt, source, tags, formats, concepts, hints?, verification?, followUps?, howTo?`; `optional` is derived by the compiler and never authored.
- **Per type:** `SpotTheErrorExercise` (`rounds: SpotRound[]` with `granularity`, `validation`, `answers`, `acceptAlso`, `fineHere`, `toolsSay`, `toolsDisagree`; `singlePick` for quizzes); `FixItExercise` (`starter`, `validation`, `goals`, `solution`, `expectStarterRules`, three `hints`); `SortExercise` (`bins` with optional `verdict`, `items` with `why`, `toolsSay`, `validityFromValidator`; `ordered`, `matrix`); `FieldExplorerExercise` (`snippet`, `fields` located by `col` or character `span`; the type requires `check` or non-empty `followUps`); `PredictExercise` (optional `snippet` shown inside the card, `items` with `input` choice/number/text/region, per-item `reveal` and `computeWith: { helper, args }`; `reveal`); `McqExercise` (`multi`, `stem`, optional `snippet`, `options` with per-option `explanation`, and `computeWith` for an arithmetic key, which the content tests recompute and require in the correct option only); `SimulatorExercise` (`simulator`, `init`, `presets`, `predictGate`, `goals` with `witness`, `textView`).
- **Embedded questions:** `FollowUp` = `EmbeddedPredict | EmbeddedMcq | EmbeddedSpot`: the type without `source`, `tags`, `formats` and `concepts`, with an `id` local to the parent. They share the parent card's status and progress record.
- **Quizzes:** `Quiz { section, title, slots, passMark, referenceCard }`; `QuizSlot { id: "2.1", tests: "<lesson-id>#<heading-id>", tags, concepts, variants, generator? }`; `QuizVariant` (mcq, predict, spot-the-error, sort; an optional `tests: "<lesson-id>#<heading-id>"` when the variant tests another heading than its slot, which the "Review:" link then uses and the key checks validate); `ParametricGenerator { id, generate(rng) }` with a seeded `Rng`; `ReferenceCard { title, items }` of table, formula or text items. Variant ids: `quiz-<section>/<slot>/<letter>`.
- **Validators** (`src/validators/types.ts`): `Diagnostic { rule, severity, verdict, line, col?, field?, file?, bytes?, message, found?, expected?, spec, toolsSay? }` (`line: 0` when no line applies; `bytes` a byte range); `RuleMeta { id, format, severity, verdict, runtime, summary, spec, toolsSay?, toolSeverity? }` where `runtime: true` means a fix-it profile uses the rule and it ships; `ValidatorProfile { include?, exclude?, escalate?, mode? }`; `ValidationContext`; `Validator`, `FolderValidator`, `GoalCheck`; and `verdictOf(diagnostics)`: any `invalid` → Invalid, else any `unusable-here` → Valid but unusable here, else Valid; warnings never decide. A diagnostic carries its own `verdict` (copied from `RuleMeta`, or set per instance where the notes make it context-dependent, such as VCF-M15). Test-only rule messages go in `src/validators/test-only-messages.json` (an array of strings) so check-dist can prove they never ship.
- **Progress** (`src/shell/progress-types.ts`): `ProgressState { schema: 1, updatedAt, lessons, quizzes, capstone, badge, prefs }` per ux-design §12.1; `ExerciseProgress { state, attempts, firstTry, revealed, answer?, updatedAt?, solvedAt? }`; `QuizProgress { best, of, passedAt, attempts, current? }` with `QuizAttempt`; keys `PROGRESS_KEY = "genomic-file-formats:v1:progress"`, `THEME_KEY`.

## 5. Widgets and the exercise card

### 5.1 The widget pattern

```ts
export class McqElement extends HTMLElement {
  data?: McqExercise; // set by the quiz page or a test; otherwise the `exercise` attribute is looked up
  card?: ExerciseCard<McqExercise>;
  connectedCallback(): void {
    if (this.card) return;
    const exercise = resolveExercise(this as ExerciseHost, "mcq"); // visible error on a bad id
    if (!exercise) return;
    const card = new ExerciseCard(this, exercise, hooks, options);
    this.card = card;
    card.body.append(/* the widget's own UI */);
    // call card.markAttempted() on input
    card.ready(); // restores saved progress through hooks.restore
  }
}
if (!customElements.get("gf-mcq")) customElements.define("gf-mcq", McqElement);
```

`src/widgets/predict.ts` is a complete example. Widgets are light-DOM custom elements; stateful widgets and simulators may render a Preact island into `card.body`.

### 5.2 `ExerciseCard` (`src/widgets/card.ts`)

- **DOM.** The card takes over the host: `.card-header` (`.card-overline` "Quick check · Multiple choice", the compiled title moved in, `.card-status`), `.card-howto`, `.card-prompt` (exercise `prompt`, inline marks), `.card-body` (yours), `.card-actions` (Check, Reset; Hint, the reveal button), `.card-confirm`, `.card-hints`, `.card-feedback` (`data-tone` success, error or neutral; `.card-verdict` with `tabindex="-1"`; `.card-explanation`) and one polite `role="status"` region. The host gets `class="exercise-card"`, `data-kind`, `data-state`, `role="group"`, `aria-labelledby` (the H3, the optional title or the Try-it H2) and `aria-describedby` (the how-to line). Its `id` stays the compiler's DOM id.
- **Hooks** (`CardHooks`, all optional): `check(): CheckOutcome` (`incomplete` with a message, `correct`, `incorrect`, or `revealed` for a predict that did not match), `reveal(): Feedback` (show the answer in the body; without it there is no reveal button), `reset()`, `restore(record)`, `answer()` (JSON-serializable), `lock(locked)`, `hasAnswer()` (quiz mode), `focusFirst()`.
- **Options** (`CardOptions`): `mode` (`lesson` or `quiz`), `overline`, `howTo`, `checkLabel` ("Lock in my prediction"), `showCheck` (false for cards that complete on their own), `showReset`, `revealLabel`, `store`, `now`.
- **Methods:** `ready()`, `markAttempted()`, `check()`, `complete(state, feedback?, { attempt?, focus? })` (for simulators reaching their goals, field-explorers finished, predicts locked), `reveal()`, `reset()` (asks first after completion; the recorded result stays), `showHint()`, `announce(text)`, quiz mode `submit(): boolean` and `hasAnswer()`. Getters: `state`, `attempts`, `firstTry`, `revealed`, `locked`, `done`, `body`, `domId`.
- **States** (`ExerciseState`): `idle → attempted → correct | incorrect`, `incorrect → attempted`, any incomplete state → `revealed`. Status labels and Lucide icons: Not started (`circle`), In progress (`circle-dot-dashed`), Not yet (`circle-x`), Correct (`circle-check`), Answer shown (`eye`).
- **Additions in M1:** a `"pending"` check outcome and `hold(verdict)` for a main answer that is right while follow-ups remain; embedded cards (`embedded: true`: no status pill, no store, no events; Ctrl+Enter checks only that card; the parent stores their records in its own `answer`); a `card.after` slot; public `restore(record)`, `clear()` and `answer()`; `complete(state, feedback, { firstTry })`; the overline can come from the host's `data-overline`.
- **Follow-ups** (`follow-ups.ts`, `followUpsFor(card, exercise.followUps)`): each `FollowUp` is an embedded card below the main feedback. A card with follow-ups saves `{ value, followUps }` as its answer and completes when the main answer and every follow-up are done; any follow-up answer shown makes the whole card "Answer shown".
- **Policy** (`REVEAL_POLICY`, ux 8.4): reveal after 2 checks (mcq, sort, field-explorer, simulator "Show me"), 3 for spot-the-error (hints after 2), 1 for fix-it ("Show solution"), always for predict ("Skip and show answer"). Hints are a ladder from `exercise.hints`.
- **Focus and announcements:** Check, Show answer and Lock move focus to the verdict line (not a live region). Hints, Reset and anything a widget announces while focus stays put go through `card.announce()`. Ctrl/Cmd+Enter checks.
- **Events** (bubbling): `gf:statechange` `{ id, state, attempts }` on every state change; `gf:solved` `{ id, state, attempts, firstTry, revealed }` exactly once per card, at the first completion, and never for a card restored as already complete. Quiz-mode cards fire neither and never touch the store.

### 5.3 Progress store

`setProgressStore(store)` installs the shell's store at boot; until then cards use a `MemoryProgressStore`. The interface is `ProgressStore { getExercise(id), putExercise(id, record), getQuiz(section), putQuiz(section, record) }` (quiz records merge with `mergeQuizProgress`, beside the other D-36 merges in `src/shell/progress-merge.ts`); `putExercise` must merge with `mergeExerciseProgress` (`src/shell/progress-merge.ts`): complete beats incomplete, correct beats revealed, the newer of two incomplete records wins, attempts take the maximum, `firstTry` and `revealed` stick once true, `solvedAt` is the earliest date, unknown keys survive. The shell stores records under `lessons[<lesson-id>].exercises[<full exercise id>]` and extends the merge to quizzes, capstone and badge (D-36).

### 5.4 Quiz mode

`gf-quiz section="sequences"` reads its `Quiz` from the registry (or from its `data` property in tests). It shows the Reference card, "Answered N of 6" and six questions it creates itself: `el.data = variant; el.dataset.mode = "quiz"; el.dataset.overline = "Question 3 of 6"`; each variant's `title` is the question heading. An attempt draws one variant per slot (authored variants first, then the slot's generator, with a seed saved in the attempt) and shuffles options; it survives a reload in `QuizProgress.current`. "Submit quiz" asks first when questions are unanswered ("Submit anyway"), calls `card.submit()` on each card (grade once, lock, explanations; no events or storage), moves focus to the results heading and shows "Passed" or "Review:" links (the variant's `tests`, else the slot's, resolved through `setHeadingResolver`, which the shell installs). The best score is kept and "Passed" is permanent; it then fires a bubbling `gf:quizsubmitted` `{ section, score, of, passed }`, which the shell uses to update the outline and pills. The `questions` getter exposes the drawn variants (the e2e walkthrough reads it).

### 5.5 Simulators

`gf-simulator` builds a card with `showCheck: false` and mounts `VIEWS[exercise.simulator]` with `SimulatorViewProps { exercise, card, onGoal(goalId, outcome?) }`; it completes the card when every goal has been reported, as Correct, or as "Answer shown" when any goal was reported with outcome `"shown"` (the per-goal "Show me"). With follow-ups (L06.2) it waits for them. A `predictGate` renders as an embedded predict card ("Predict first") above the island; the island mounts only once the prediction is locked in or skipped, a prediction that did not match ends the card as "Answer shown", and the gate's record is saved in the card's answer (`{ gate, followUps }`). Reset clears the gate and remounts the island. Each simulator exports a pure `SimulatorModel { init, reduce, goalChecks, text }` (`src/widgets/simulators/types.ts`, `TextView` = table, list or log) registered in `models.ts`; content tests replay every goal's `witness` through it. Each `model.ts` header lists its init arguments, actions and goal checks:

- `fai-calculator`: goal checks `showsBase { position, row?, convention? }`, `showsByte { byte, row? }`, `comparedRows { position, rows }`; actions `position` (1-based), `p` (0-based), `byte`, `preset { state }` (a `row` is enough to switch files), `field`, `step`, `line`, `convention`.
- `bgzf-demo`: `fetched { mode?, position?|target? }`, `comparedModes`, `eofChecked { present }`; actions `step`, `mode`, `position`, `target`, `restart`, `eof`, `checkEof`, `preset`. Play is hidden under reduced motion; it never autoplays.
- `phred-converter`: `decoded { chars }`, `showsQ`, `showsChar`, `qualityIs`; actions `char`, `q`, `p`, `step`, `quality`, `preset`; `init.sum: false` hides the expected-errors sum so follow-ups can ask for it.

`shared.tsx` holds `useSimulator` (goal detection and per-goal "Show me" after two tries), `Goals`, `Readout` (a polite region that waits 500 ms and is silent on mount), `TextViewBlock`, `Presets` and `NumberField`. `test-fixtures.ts` has working exercises for each simulator: copy from it when authoring.

### 5.6 Viewers, icons and inline text

- `renderSnippet(snippet, { mode?, view?, label? })` (`read`, `pick-line`, `pick-field`, `explore`), `renderHexView(snippet, options)` and `renderCompressedText(snippet, options)` return elements; `renderSnippetFigure(snippet)` adds the caption. `gf-snippet` renders a registered snippet. Text viewers have raw and aligned views, whitespace markers, CR, no-newline and code-point chips, a "Lengths and separators" gutter (each line's description, also in its accessible name; on by default in spot-the-error rounds except below 600 px), "View as table", Copy and Download. Interactive modes are a `role="grid"` with a roving tabindex and cells of at least 24 × 24 px.
- `icon(name, { label?, className? })` returns SVG markup (decorative unless labelled); `hydrateIcons(root)` fills `[data-icon]` placeholders. Add an icon by importing it in `src/shell/icons.ts`; never use text glyphs for marks.
- Strings in exercise data may use `` `code` ``, `*italic*` (gene symbols), `**bold**` and `^{sup}`; render them with `inlineNodes` / `inlineHtml` (`src/widgets/inline.ts`), which escape everything else.

## 6. Shell

`src/main.ts` boots `src/shell/app.ts`, which renders every route of D-22 from `virtual:lessons` and the manifest: home, lessons, quiz pages, capstone, badge, About and "Not found"; planned pages show a "not built yet" page. On a route change it renders, sets `document.title`, scrolls and moves focus to the H1 or the deep-link target (on first load focus stays at the top so Tab reaches the skip link). A hash change to another heading of the page already shown scrolls instead of re-rendering, so widgets keep their state.

- **Aside:** the switcher card ("Lesson N of 22 · Sequences", a course progress bar over the 30 outline items) expands into the course outline (status icons, "Passed" pills, a locked badge row; planned rows muted and not linked); the scroll-spy TOC with "Try it" status icons (on the quiz page: Question 1-6 and Results); the theme menu (System, Light, Dark; the inline head script applies it before first paint; other tabs follow).
- **Below 1080 px:** a sticky top bar opens a modal sheet with "On this page" and "Course outline" tabs.
- **Lesson chrome:** prev/next cards (`a.pager-prev`, `a.pager-next`), the status line ("N exercises left in this lesson" with links, or "Lesson complete"), a scripted skip link. A lesson counts as complete when all its graded (non-optional) exercises are complete.
- **Progress** (`CourseStore`, `progress-store.ts`): a storage probe at boot; every write merges with what is stored (D-36; debounced 300 ms, flushed on `pagehide` and when hidden); `storage` events from other pages merge in; unknown keys survive; a newer schema is left untouched; an unreadable value is backed up under `…:unreadable`. Methods: `getExercise`, `putExercise`, `getQuiz`, `putQuiz`, `visit`, `markBadgeEarned`, `importState(state, "merge" | "replace")`, `subscribe`, `onPersistence`, `flush`, `toJson`. Without storage, progress stays in memory, a notice shows and the footer reads "Progress not saved".
- **Progress code** (`progress-code.ts`): `GF1Z.<base64url deflate-raw JSON>.<crc32>` (or `GF1U.` uncompressed), without answers; import merges unless the learner picks "Replace my progress". "Download progress (.json)" saves the full state with answers.
- **Home and About:** home has the intro, objective, pipeline map, outline, "Continue" and the progress tools; About has the version, pinned versions, data sources and the license texts, imported at build time from `LICENSE` and `LICENSES/`.

## 7. Validators

- **Runtime (ships):** `src/validators/runtime/index.ts` exports `validateRuntime(validation, text)`, `checkGoals(goals, text, context)`, `formatDiagnostic(d)` (the 8.4 line), `SNIPPET_LIMITS` and `withinSnippetLimits` (300 lines, 64 KB), `RUNTIME_RULES` and `GOAL_CHECKS`. `runtime/fasta.ts` holds the fix-it rules FA-S01, FA-S03 and FA-M01; `runtime/goals.ts` the goal checks `fastaKeepsBases`, `fastaKeepsRecords` and `fastaUniqueNames`. Shipped modules import only `runtime/` and `core.ts`; a unit test checks the import graph.
- **Test-only:** `fasta.ts` (FA-S01-S06, M01, M03, M06, C04), `fai.ts` (FAI-S01, S02, M01 against the FASTA, M02), `fastq.ts` (FQ-S01-S06, M01, C01, C04; records parsed by length, as Biopython and htslib do), `gzip.ts` (GZ-S01 "unusable here", GZ-S02 Invalid, and CASE-14 on hex summaries; `ValidationContext.requireBgzf`), `folder.ts` (`validateFolder`, CASE-14), `all.ts` (the registry of every rule and validator), `keys.ts` (the content key checks, `snippetsIn`, `seededRng`, `GENERATOR_SEEDS`), `fixtures.ts`. ## 11. Gotchas

- Relative imports carry their `.ts`/`.tsx` extension (nodenext); type imports use `import type`; no enums.
- Exercise, quiz and case modules are pure TS: no DOM, CSS, `?raw` or Vite-only imports (the plugin evaluates them in Vite's module runner).
- Write TAB and CR in snippet text as `\t` and `\r`; a test rejects raw U+000D under `src/` and `content/`.
- Genomic tokens like `<DEL>` go in backticks in Markdown and data strings.
- The shipped file must not contain the denylisted brand terms (`scripts/brand-denylist.txt`), in code comments that survive minification either.
